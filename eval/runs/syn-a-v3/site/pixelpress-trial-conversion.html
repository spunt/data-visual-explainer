1 The gist · for everyone

What share of people who start a PixelPress Pro free trial become paying subscribers?

14.3%

Among mobile users whose started from 2 through 9 March 2026, 14.3% had a on after start.

6,894 of 48,210 trial users had a positive charge in the implemented window.

≈About 14 in every 100 users in the implemented first-trial mobile had a positive charge by day 14.

What kind of claim: Describes a level. This number describes what happened in one group. It does not compare groups or explain why.

✓ Safe to say

"In the saved March run, 14.3% of first recorded PixelPress Pro mobile trial users had a positive charge on days 0-14 after trial start."

✗ Not this

"The new onboarding caused a 1.4-point lift," or "the metric used a 30-day window ending 8 March."

Now the general rule, one step at a time. Each step has the plain version, with the exact version one click away.

  1. Step 1 · Who is counted

    Start with users, then apply each rule

    One PixelPress Pro mobile user.

    Exactly

    One distinct user_id from app.trial_events after taking MIN(trial_start_date) per user for product = 'PIXELPRESS_PRO' and platform IN ('ios', 'android').

    S3

  2. Step 2 · When the clock starts

    Time zero: first recorded trial start

    Each user's clock starts on their first recorded PixelPress Pro mobile trial date.

    • Positive-charge window: Trial start day through day 14 after trial start. A charge on day 14 still counts. (days 0–14)
    Exactly

    trial_start_date is MIN(t.trial_start_date) per user_id from the trials CTE.

    S3

  3. Step 3 · What counts

    Had a positive charge

    Counts a user if they had at least one charge above zero dollars in the window.

    Exactly

    first_charge joins billing.charges where b.user_id = c.user_id, b.amount_usd > 0, and b.charge_date falls in the inclusive charge window, then groups to MIN(b.charge_date). The final summary counts DISTINCT f.user_id.

    S3

  4. Step 4 · Combine

    Turn yes/no answers into a share

    Divide users with a positive charge by all users in the implemented cohort.

    Exactly

    ROUND(100.0 * COUNT(DISTINCT f.user_id) / COUNT(DISTINCT c.user_id), 2) AS conversion_rate_pct.

The same definition, assembled mechanically from the spec

Generated from the structured definition, not written by hand. If it disagrees with the summary above, the summary is wrong.

  1. The unit is one user. One PixelPress Pro mobile user.
  2. Keep users that meet every rule, in order: users with at least one PixelPress Pro trial event on iOS or Android; each user is assigned their first recorded PixelPress Pro mobile trial date; the first recorded trial date is from 2 through 9 March 2026.
  3. Time zero is the first recorded trial start: Each user's clock starts on their first recorded PixelPress Pro mobile trial date.
  4. Positive-charge window (outcome): days 0–14, counting the first recorded trial start as day 0.
  5. For each user, record had a positive charge (headline) as yes/no within the positive-charge window: Counts a user if they had at least one charge above zero dollars in the window.
  6. Divide users with a positive charge by all users in the implemented cohort.
  7. Do this separately for each group: March 2026 first-trial mobile cohort.
  8. No confidence interval or standard error was reported for the 14.3% headline.

3 Keep in mind · before you act on it

Judgment calls

Which headline to document

Chose: Use the 14.3% March conversion rate as the headline, because it is the first number in the readout and is backed by the saved CSV.

Could have chosen: Write a separate card for the 1.4-point March-versus-February lift.

Why: The February rate and lift are quoted in the readout but no February output or comparison code is included in the fixture.

What it changes: The card explains the measured March level and treats the lift as readout-only, not independently reproducible.

How to express the outcome window

Chose: Describe the implemented SQL as days 0-14, rather than repeating the README's 30-day definition.

Could have chosen: Treat the README as authoritative and mark the saved SQL/result as incompatible with the stated metric.

Why: The skill says to trace the number to code and write from the implemented rule.

What it changes: Readers see that the 14.3% number is not evidence for a 30-day conversion rate.

Where the description and the code disagree

Outcome window length

Described

README and readout define conversion as paying within 30 days of trial start.

Implemented

params sets conversion_days = 14, and first_charge keeps charge_date BETWEEN trial_start_date AND DATE_ADD(trial_start_date, 14), inclusive.

Impact: A shorter window likely understates the 30-day conversion rate. The size is unknown from the saved files.

S1S2S3

Cohort date range

Described

README says trials started 2026-03-02 through 2026-03-08.

Implemented

SQL sets cohort_end to DATE '2026-03-09' and uses BETWEEN, so 9 March starts are included.

Impact: The implemented denominator can include an extra start date. Direction and size are unknown.

S1S3

Internal and test account exclusions

Described

README says internal and test accounts are excluded.

Implemented

No internal-account or test-account filter appears in the saved SQL.

Impact: If such accounts exist in app.trial_events, they remain in the result. Direction and size are unknown.

S1S3

Refund exclusion

Described

README says refunded charges do not count.

Implemented

SQL joins billing.charges with b.amount_usd > 0, but shows no refund, reversal, or net-paid filter.

Impact: Refunded positive charges could overstate net-paid conversion. The size is unknown.

S1S3

First trial versus any trial

Described

Descriptions say users who started a trial in the cohort week.

Implemented

SQL first takes MIN(trial_start_date) per user across PixelPress Pro mobile trial events, then filters that first recorded trial into the cohort.

Impact: Users with an earlier PixelPress Pro mobile trial and another trial in March are excluded. Direction and size are unknown.

S1S2S3

Onboarding lift claim

Described

The readout says the new onboarding is driving a 1.4-point lift and recommends rolling it out to web.

Implemented

The saved SQL computes a single March cohort rate only. No February cohort SQL, web cohort, counterfactual, adjustment, or uncertainty is included.

Impact: The fixture supports a descriptive March rate, not a causal onboarding claim or web rollout inference.
