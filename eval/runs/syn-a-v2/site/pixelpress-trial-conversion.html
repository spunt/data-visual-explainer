What kind of claim: Describes a level. This number describes what happened in one group. It does not compare groups or explain why.

Now the general rule, one step at a time. Each step has the plain version, with the exact version one click away.

  1. Step 1 · Who is counted

    Start with trial users, then apply each rule

    One PixelPress Pro mobile user with a trial start.

    Exactly

    One distinct t.user_id after taking MIN(t.trial_start_date) from app.trial_events where product = 'PIXELPRESS_PRO' and platform IN ('ios', 'android').

    S3

  2. Step 2 · When the clock starts

    Time zero: first trial start

    Each user's clock starts on the day they first started a PixelPress Pro mobile trial.

    • March cohort entry: A user's first trial start has to fall in the March cohort dates. (day 0)
    • SQL conversion watch window: The saved SQL watches for a paid charge from the trial start day through day 14. (days 0–14)
    Exactly

    trial_start_date = MIN(t.trial_start_date) per user_id in the trials CTE.

    S3

  3. Step 3 · What counts

    Converted to paid

    Counts a if they had at least one positive charge in the SQL outcome window.

    Exactly

    first_charge has one row for users with MIN(b.charge_date) after joining billing.charges on user_id with b.amount_usd > 0 inside the conversion window; converted users are COUNT(DISTINCT f.user_id).

    S3

  4. Step 4 · Combine

    Turn yes/no answers into a share

    Divide converted trial users by all trial users in the cohort and report it as a percent.

    Exactly

    ROUND(100.0 * COUNT(DISTINCT f.user_id) / COUNT(DISTINCT c.user_id), 2) AS conversion_rate_pct.

Generated from the structured definition, not written by hand. If it disagrees with the summary above, the summary is wrong.

  2. Keep trial users that meet every rule, in order: people who started a PixelPress Pro trial on iOS or Android; users whose earliest trial start falls in the SQL's March cohort window.
  3. Time zero is the first trial start: Each user's clock starts on the day they first started a PixelPress Pro mobile trial.
  4. March cohort entry (eligibility): day 0, the first trial start itself.
  5. SQL conversion watch window (outcome): days 0–14, counting the first trial start as day 0.
  6. For each trial user, record converted to paid (headline) as yes/no within the sql conversion watch window: Counts a trial user if they had at least one positive charge in the SQL outcome window.
  7. Divide converted trial users by all trial users in the cohort and report it as a percent.
  8. Do this separately for each group: March 2026 mobile SQL cohort.
  9. No confidence interval or standard error was reported with the 14.3% headline.

3 Keep in mind · before you act on it

What could make this misleading

Complete. The latest first trial start is 09 Mar 2026; its SQL conversion watch window ends 23 Mar 2026. Data are complete through 17 Apr 2026, so every window is fully observed. This number should not move as more data arrive.

Prose and SQL use different conversion windows

The project note and readout call the metric 30-day conversion, but the query parameter is 14 days. If a 30-day rerun were made, the rate could be higher.

May make the number look smaller than it really is · high importance S1 S2 S3

↕

Exclusion and refund rules are not visible in the SQL

The project note says internal and test accounts are excluded and refunded charges do not count. The query shown filters only product, platform, and amount.

Could push the number either way · high importance S1 S3

↕

Cohort end date differs by one day

The project note says the is 2026-03-02 through 2026-03-08, but the query uses an inclusive date filter ending on 2026-03-09.

Could push the number either way · medium importance S1 S3

◎

The February comparison is not reproducible from the saved files

The readout says March is up from 12.9% in February, but the saved query and results table only contain the March cohort summary.

Limits what the number can be used to conclude · medium importance S2 S4

Where the description and the code disagree

Conversion window

Described

The project note and readout define conversion as paying within 30 days of trial start.

Implemented

The query sets conversion_days = 14 and filters b.charge_date through DATE_ADD(trial_start_date, 14).

Impact: A longer 30-day window would include later converters, so the saved 14.3% may understate the intended 30-day conversion rate. The size is unknown.

S1S2S3

Cohort end date

Described

The project note says trials started 2026-03-02 through 2026-03-08.

Implemented

The query sets cohort_end to DATE '2026-03-09' and uses an inclusive date filter.

Impact: The SQL appears to include one extra trial-start date. Direction and size are unknown.

S1S3

Internal and test account exclusions

Described

The project note says internal and test accounts are excluded.

Implemented

The provided SQL does not show an internal-account or test-account exclusion.

Impact: If those accounts exist in app.trial_events, they may affect the denominator and numerator. Direction and size are unknown.

S1S3

Refunded charges

Described

The project note says refunded charges do not count as paying.

Implemented

The provided SQL requires b.amount_usd > 0 but does not show a refund or net-paid filter.

Impact: Refunded positive charges could overstate paid conversion if the billing table does not already remove or net them out. Size is unknown.

S1S3

Onboarding lift claim

Described

Readout says the new onboarding flow is driving a 1.4-point lift versus February.

Implemented

The saved query and results table provide one March cohort rate and no causal comparison or February cohort computation.

Impact: The 14.3% March level is reproducible from the saved output; the 1.4-point causal lift is not reproducible from the provided files.
